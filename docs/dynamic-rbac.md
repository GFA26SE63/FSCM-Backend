# Dynamic RBAC contract

REST business actions, entity GraphQL fields and aggregate GraphQL queries require the exact `api:Controller.Action` grant **and** a selected screen linked to it in `SYS_SCREEN_API_MAPPING`. Authentication reloads grants from the assigned `SYS_ROLE` on each HTTP request. Mapping reads are request scoped; changing grants or mappings applies to the next request with the same JWT. Unknown operations fail closed. Authentication endpoints and the private notification inbox retain their own authentication/ownership rules.

The role editor submits selected screen codes. The backend derives API dependencies from the persisted mapping and ignores client supplied API additions. A screen has the same initial operation contract across business profiles. `InitialRoles` and `ScreenOperationDependencies.Rest` describe bootstrap reference data, never runtime operation ceilings. Administrators can change persisted mappings without recompiling. API capabilities must still be registered in `ApiPermissionCatalog`.

`BaseRole` remains the business data-scope profile: global operations, assigned warehouses, sales groups, or linked retailer. Delegating a screen does not grant unassigned stock, another warehouse trip, or another retailer account. Application ownership, state, concurrency, idempotency, refund separation of duties and audit checks remain authoritative. REST transaction references reuse scoped entity queries; warehouse shipment commands additionally require the actor's assigned warehouse. Explicitly delegated user/role administration reads receive the global directory needed by that administration screen. Private notifications always remain recipient scoped.

The protected system Admin retains full administration access and cannot be repurposed as a custom role. Checks on a **target** account's profile, protected Admin, and business data scope are invariants, not operation allowlists.

Frontend action controls use exact API grants and navigation uses screen grants. Mobile route admission and reusable authorization widgets use grants rather than a list of profiles; delegated screens are discoverable from the account screen. Missing/empty permission arrays grant no business screens. Cached clients may display stale controls until profile refresh, but every server request rechecks live permissions.

Forward-only data migrations `20261127120000_UnifyDynamicScreenOperationGrants` and `20261127130000_MapDelegatedTransportReads` synchronize dependencies and backfill only the APIs of already-selected screens. They do not select new screens, provision business accounts, seed, reset or delete data. Dispatch transport lookups use typed, cursor-paginated GraphQL; assignment/departure/receipt remain REST commands. No route or DTO breaking change is introduced.
